# 出生档案 `v2-phase4b` 的由来（上市日缺陷与修正）

> 本文记录一次**影响 1,181 只股票出生日的数据缺陷**、修正过程与验证结果。
> 需要它才能解释"为什么同一只股票上个月算出来的盘和今天不一样"（`AGENTS.md` §11）。

## 缺陷是什么

Phase 4 建 `v4-full`（6,104 只）时，对 `stock_master.listing_date` 为 NULL 的股票
用**行情数据首根日线**补齐。这个模式来自 `scripts/fetch_market_import.py` 的
`"listing_date": dates[0]`。

问题在于供应商行情数据的**覆盖起点**：

* 沪深老股的行情从 **2000-04-03** 开始 → 474 只老股的"上市日"被写成 2000-04-03
  （平安银行 000001、万科A 000002 实际是 1991 年上市）
* 北交所股票的覆盖起点是 **2025-10-09** → 243 只落入同一天

**后果**：447 只老股共用同一个出生时刻 → **八字盘完全相同** → 它们的因子观测
在横截面上完全重复，会虚增有效样本量。6,104 只股票当时只有 2,710 个不同的出生时刻。

**发现方式**：`scripts/astrology_calendar.py screen` 的输出出现异常——
300 只里有 150 只拿到完全相同的契合度和关系串，且代码连号（000001–000008）。

## 修正后的来源与优先级

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | 用户提供的权威表（`日柱.xlsx` 的「上市日期」列） | 覆盖 5,395 只 |
| 2 | TuShare `stock_basic`（`data/import/tushare_stock_basic.csv`） | 兜底，补齐用户表未覆盖的 715 只（含北交所 313 只） |
| 3 | 两者都没有 | **保留原值并打标**，不猜测（实际为 0 只） |

TuShare 数据由 `scripts/phase4c_fetch_tushare_basic.py` 获取（标准库 `urllib`，
不引入新依赖；token 从环境文件读取且不打印）。抓取在市 5,565 + 退市 339 = 5,904 条。

## 交叉验证（这是最有力的证据）

| 对比 | 结果 |
|---|---|
| 用户权威表 ∩ TuShare（5,147 只重合） | **一致率 100.00%，零分歧** |
| 两份来源合计覆盖 | **6,104 / 6,104 = 100%** |
| 用户表 vs 公开已知上市日（12 只人工抽查） | 12/12 一致 |

两个**完全独立**的来源逐只吻合，因此用户表可以作为权威口径使用。

另外把用户表里的四柱与**本项目引擎**做了独立比对（250 只抽样）：
年柱 100%、日柱 100%、时柱 100% 一致；月柱 247/250。

> 月柱那 3 例差异经节气精确时刻判定为**用户表的问题**（它按"整日"切换月柱）：
> 1993-10-08 寒露在 **14:40:02**、1996-11-07 立冬在 **11:26:33**，而上市开盘 09:30
> 都在节气时刻之前，故仍属上一月。本项目引擎按节气精确时刻切换，口径正确。
> 结论：表里的年柱/日柱/时柱可直接使用，**月柱在"节气当天出生"这类（约 1.2%）上不能用**。

## 修正结果

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 上市日仍为可疑值 | 723 只 | **0** |
| 出生档案标"不可用" | 249 只 | **0** |
| 重复出生时刻最大一组 | 447 只 | **54 只** |
| 覆盖股票名称 | 5,601 行空 | 全部补齐 |

修正共 **1,181 只**（916 只用用户表 + 265 只用 TuShare），其中
**1,141 只的出生时刻发生变化**（其余是名称/退市股等无出生档案的行）。

剩下的重复出生时刻**都是真实历史事实**：2020-07-27 精选层首批 54 只、
创业板首批 28 只（2009-10-30）、科创板首批 25 只（2019-07-22）、
北交所开市首批 22 只（2021-11-15）、创业板注册制首批 18 只（2020-08-24）。

## 版本与影响范围

* 出生档案提升为 **`v2-phase4b-*`**（`listing_open` / `listing_close` / `ipo_approx`）；
  `v1-phase3b-*` **保留不删**，Phase 3 的产物仍可复现
* **未修正的 15,669 行在两个版本间逐值相同**（已验证），因此新旧版本可以安全拼合
* `company_foundation` 仍按规则保持 UNAVAILABLE（不落库）
* 面板采集器（`scripts/phase3d_collect_panel.py` 的 `MODEL_VERSIONS`）已指向 v2

**对已有结论的影响**：Phase 3 的核心结论**不受影响**——`v2-phase3a`（500 只）
里命中该缺陷的是 **0 只**。受影响的是 Phase 4 的全市场面板：
其中 1,141 只用的是旧出生档案，需要按 v2 重算后拼回
（`scripts/phase4d_splice_panel.py`；面板按股票分片，不必全量重跑）。

## 回滚

* 上市日修正清单（含旧值）：`data/phase4_cache/listing_date_corrections.csv`
* 旧值来源规则：**旧值 = 供应商行情首根日线**（可精确复现，已用它重建过一次审计
  清单并逐分布核对通过）
* 面板拼合前的原件：`data/phase4_cache/merged_panel_pre_resplice.pkl`
* 出生档案：`v1-phase3b-*` 行完整保留，无需回滚动作

* 用户表未覆盖北交所等 715 只，其上市日来自 TuShare——比供应商起点可靠，但
  对北交所而言"上市日"本身有歧义（新三板挂牌 / 精选层 / 北交所上市三个口径）
* `stock_birth_profile` 的 `listing_open` 有 4 只重复行（000024 / 002008 /
  300750 / 600519），疑似 `autoflush=False` 下的幂等陷阱，尚未清理
